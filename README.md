# sss-backup

แตกไฟล์เป็นหลายชิ้นด้วย **Shamir's Secret Sharing** — ใช้เพียงบางชิ้นก็กู้ไฟล์เดิมกลับมาได้ครบ 100%

ตัวอย่าง 3-of-5: แตกไฟล์เป็น 5 ชิ้น เก็บกระจายไว้คนละที่ ชิ้นไหนหายไป 2 ชิ้นก็ยังกู้ได้ แต่ใครที่ได้ไปแค่ 1–2 ชิ้นจะประกอบอะไรไม่ได้เลย

เขียนด้วย Python ล้วน ใช้เฉพาะไลบรารีมาตรฐาน ไม่ต้อง `pip install` อะไรทั้งนั้น

---

## เริ่มใช้งาน

```bash
# แตกไฟล์เป็น 5 ชิ้น ใช้ 3 ชิ้นก็กู้ได้
python sss_backup.py split secret.pdf -k 3 -n 5

# กู้คืน (สแกนหา share ในโฟลเดอร์เองอัตโนมัติ)
python sss_backup.py restore ./shares

# หรือเปิดเมนูโต้ตอบ
python sss_backup.py
```

ต้องใช้ Python 3.6 ขึ้นไป

## หลักการทำงาน

### จุดกับเส้นโค้ง

จุด 2 จุดกำหนดเส้นตรงได้เส้นเดียว จุด 3 จุดกำหนดพาราโบลาได้เส้นเดียว

ถ้าซ่อนความลับไว้ที่ค่า y ตอน x = 0 ของพาราโบลา แล้วแจกจุดบนเส้นนั้นออกไป 5 จุด ใครมี 3 จุดก็ลากเส้นย้อนกลับมาหาค่าที่ x = 0 ได้ แต่ถ้ามีแค่ 2 จุด จะมีพาราโบลานับไม่ถ้วนที่ลากผ่านทั้งสองจุดนั้น — ทุกค่าที่ x = 0 มีโอกาสเป็นไปได้เท่ากันหมด

นี่คือ **information-theoretic security** ไม่ใช่แค่ "ถอดยาก" แต่คือข้อมูลไม่พอทางคณิตศาสตร์ ต่อให้มีคอมพิวเตอร์แรงแค่ไหน หรือควอนตัมคอมพิวเตอร์ ก็เดาไม่ออก

### ทำไมต้อง GF(256)

ถ้าใช้จำนวนจริงจะเจอปัญหาปัดเศษและตัวเลขบวม จึงคำนวณใน **finite field ขนาด 256** ซึ่งพอดีกับ 1 ไบต์เป๊ะ:

| การดำเนินการ | ใน GF(256) |
|---|---|
| บวก / ลบ | XOR |
| คูณ / หาร | ตาราง log-exp บน polynomial `0x11B` (ตัวเดียวกับ AES) |

จากนั้นทำทีละไบต์: ไบต์แรกของไฟล์ใช้พาราโบลาเส้นหนึ่ง ไบต์ที่สองสุ่มสัมประสิทธิ์ใหม่เป็นอีกเส้น ไปเรื่อยๆ share ชิ้นที่ x คือค่า f(x) ของทุกไบต์เรียงต่อกัน

### รหัสผ่านทำงานคนละชั้น

ลำดับสำคัญมาก — **เข้ารหัสก่อน แล้วค่อยแตกเป็น shares**

```
ไฟล์ต้นฉบับ
   -> ผนวก metadata (ชื่อไฟล์, ขนาด, SHA-256)
   -> เข้ารหัสด้วยคีย์จากรหัสผ่าน
   -> แตกเป็น n shares
```

ถ้าทำสลับกัน คนที่เก็บ shares ครบ k ชิ้นจะเปิดไฟล์ได้ทันทีโดยไม่ต้องรู้รหัสผ่าน

- **KDF**: scrypt (N=2^15, r=8, p=1) ตั้งใจให้ช้าเพื่อกัน brute force
- **Cipher**: HMAC-SHA256 counter mode + encrypt-then-MAC

## รูปแบบไฟล์ share

ทุกอย่างที่จำเป็นต่อการกู้คืนถูกฝังไว้ใน header ของ share **ทุกชิ้น** ไม่ต้องพึ่งไฟล์ metadata ภายนอกเลย มี share ครบ k ชิ้นก็กู้ได้

```
+--------- header 78 ไบต์ ---------+
| magic    "SSS53\0"       6 ไบต์  |
| version                  1 ไบต์  |
| x (พิกัดของ share)        1 ไบต์  |
| k (ขั้นต่ำที่ต้องใช้)       1 ไบต์  |
| n (จำนวนทั้งหมด)          1 ไบต์  |
| salt                    16 ไบต์  |
| nonce                   16 ไบต์  |
| tag (HMAC)              32 ไบต์  |
| payload length           4 ไบต์  |
+----------------------------------+
| payload (เท่าขนาดไฟล์ต้นฉบับ)      |
+----------------------------------+
```

ชื่อไฟล์เดิมกับ SHA-256 ถูกซ่อนอยู่ **ข้างใน** ส่วนที่เข้ารหัส — share ที่หลุดออกไปจึงไม่บอกใบ้ว่าข้างในคือไฟล์อะไร

ไฟล์ `manifest.json` ที่สร้างมาด้วยมีไว้ให้คนอ่านเฉยๆ ลบทิ้งได้ ไม่กระทบการกู้คืน

## สิ่งที่ระบบนี้ป้องกันได้ และไม่ได้

**ป้องกันได้**

- ชิ้นส่วนหายหรือเสียหายได้ถึง n − k ชิ้น
- ผู้ที่ได้ share ไปน้อยกว่า k ชิ้น ไม่ได้ข้อมูลอะไรเลย
- ผู้ที่ได้ share ครบ k ชิ้นแต่ไม่มีรหัสผ่าน ก็ยังเปิดไม่ได้
- ตรวจจับได้ทันทีถ้ารหัสผ่านผิดหรือข้อมูลถูกแก้ไข

**ป้องกันไม่ได้**

- ถ้ารหัสผ่านอ่อน และคนร้ายได้ share ครบ k ชิ้น → brute force ได้ (scrypt แค่ทำให้ช้าลง)
- ยังไม่รองรับการระบุว่า share ชิ้นไหนเสีย — รู้แค่ว่าประกอบแล้วไม่ผ่าน MAC
- ไม่ได้ล้างคีย์ออกจากหน่วยความจำหลังใช้งาน

## เรื่องที่ต้องระวัง

**อย่าเก็บ share ครบ k ชิ้นไว้ที่เดียวกัน** ไม่งั้นจะเสียจุดประสงค์ทั้งหมด แนวทางที่ควรทำ:

| ชิ้น | ที่เก็บ |
|---|---|
| part1 | คอมพิวเตอร์ที่บ้าน |
| part2 | USB ในตู้เซฟ |
| part3 | คลาวด์ |
| part4 | ให้คนที่ไว้ใจ |
| part5 | สำนักงาน |

**อย่า commit ไฟล์ `*.bin` ขึ้น repo** — ไฟล์ `.gitignore` ในโปรเจกต์นี้กันไว้ให้แล้ว

**พื้นที่ที่ใช้** แต่ละ share มีขนาดเท่าไฟล์ต้นฉบับ ดังนั้น n = 5 กินพื้นที่รวมประมาณ 5 เท่า นี่เป็นข้อจำกัดโดยธรรมชาติของ SSS ถ้าต้องการประหยัดพื้นที่ ต้องเปลี่ยนไปใช้ erasure code แบบ Reed–Solomon แทน แต่จะไม่ได้ความปลอดภัยระดับ information-theoretic

## ทดสอบ

```bash
python -m unittest test_sss_backup -v
```

29 การทดสอบ ครอบคลุมตารางคูณ GF(256) ครบทั้ง 65,536 คู่, ทุกชุดผสมของ k จาก n, การปฏิเสธรหัสผ่านผิด, ไฟล์ว่าง, ชื่อไฟล์ภาษาไทย, การที่ share ไม่รั่วชื่อไฟล์ และการพิมพ์ผลบนเทอร์มินัลที่ไม่รองรับ UTF-8

### กับดักที่เจอตอนพัฒนา

**ตัวสร้างของตาราง log** ต้องใช้ตัวคูณ **3** ไม่ใช่ 2 เพราะเลข 2 ในสนามนี้มี multiplicative order แค่ 51 ไม่ครบ 255 ถ้าใช้ผิด โปรแกรมจะรันได้ปกติ ไม่มี error แต่กู้ไฟล์ไม่ได้เลย เทสต์ `gf_mul(3, 7) == 9` จับเคสนี้ได้

**Encoding บน Windows** เมื่อ stdout ถูก redirect เข้า pipe หรือไฟล์ Python จะไม่ใช้ console encoding แต่ถอยไปใช้ locale encoding ซึ่งบน GitHub Actions คือ cp1252 → `print()` ข้อความไทยแล้ว `UnicodeEncodeError` ทันที (`sys.stderr` ไม่พังเพราะตั้ง `errors='backslashreplace'` ไว้แล้ว แต่จะได้ `\u0e1e\u0e1a` แทนตัวอักษรจริง) แก้ด้วย `reconfigure()` ตอนโหลดโมดูล บวกกับฟังก์ชัน `out()` ที่ดักไว้อีกชั้น
